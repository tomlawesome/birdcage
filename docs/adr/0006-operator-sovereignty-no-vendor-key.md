# ADR-0006: Every deployment's trust root belongs to its operator; birdcage's authors hold no key

**Status:** Accepted
**Date:** 2026-09-16
**Relates to:** #50 (agent binary signing), #48 (the agent), #47
(enrolment), #32 (ingest transport and the command channel).

## Context

#32's command channel can, in principle, carry an `upgrade` command that
installs a binary on every canary. #32's own threat model states the
consequence plainly: "an attacker who compromises birdcage itself owns the
fleet."

Working through how to stop that (#50, 2026-09-16) the discussion arrived
at code signing, and then at the obvious question of where the private key
lives. The first shape proposed was a single signing key held by the
project's author, with each agent pinning the matching public key.

The owner rejected it: *"if anyone gets the signing key from me, EVERY
instance of birdcage in existence is compromised"*, and then stated the
principle behind the rejection: *"Administrators must have control and
sovereignty over their own instance. Me having the master key is
unacceptable."*

That is a correct reading. A single vendor key across every deployment is
a single point of total failure for every operator at once, and it is the
SolarWinds shape: one theft, every installation. It also quietly makes
every operator depend on the author's personal operational security, which
they cannot inspect, audit or improve.

## Decision

**1. No vendor key is ever in any deployment's trust path.** The project's
authors hold no key, of any kind, that can cause an agent anywhere to
accept anything. This is not a default to be overridden by configuration:
there is no configuration that turns it on.

**2. A deployment's trust root is generated by that deployment, at
install, and belongs to its operator.** If agents verify anything, they
verify it against a key their own operator holds. Birdcage may hold the
public half; it never holds the private half.

**3. Any published checksum or signature from the project is
verification material an operator may choose to use, never a trust root an
agent requires.** Reproducible builds and published digests let an
operator satisfy themselves that a binary is genuine. The difference is
who decides: the operator, out of band, rather than a key the project
controls.

## Consequences

- **The blast radius of any key loss is one deployment.** That also makes
  #50's "what if the key is lost" question tractable: the answer is scoped
  to one operator's own fleet, and re-enrolment is bounded by that fleet's
  size rather than by the whole installed base.
- **Birdcage cannot ship agent upgrades to operators as a product
  feature.** Not "must not by policy" -- it structurally cannot, because
  it holds nothing any agent will trust. Whether an upgrade path exists at
  all, and what it looks like, is now a question about what the *operator*
  can authorise from off the box, and is open on #50.
- **The `upgrade` command stays unmintable.** `store.CommandKind` is a
  closed set containing only `selftest` (slice 5b, 2026-09-16), pinned by
  TestUpgradeCommandCannotBeMinted. Nothing in this ADR changes that, and
  widening it needs the open question above answered first.
- **Enrolment (#47) carries the weight.** A canary enrolled after a
  birdcage is compromised pins whatever it is told to pin. Whatever
  verification exists must reach a new canary by a path that is not the
  compromised server's own UI.
- **This constrains #48's design** before it is built, which is the point
  of recording it now rather than after.

## Superseded

- *A single project-held signing key, pinned by every agent in every
  deployment* (proposed and rejected the same day, 2026-09-16). Recorded
  so it is visibly closed rather than overlooked: it is the conventional
  answer, it will be proposed again, and the reason it is refused here is
  a principle about who owns a deployment rather than a judgement about
  how well a key can be stored.
