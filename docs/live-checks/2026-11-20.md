script). One enrolled canary with all four of its containers was attacked from
a separate attacker container, and every alert was followed to the API and the
dashboard. Everything ran in rootless Docker on one `docker network create
--internal` network; nothing was reachable off the host, and the only pulls
were by digest from the project registry. No real addresses appear here:
`<attacker>` is the attacker container, `<canary>` the canary's holder, and
`<answerer>` the poisoner fixture.

## Setup

- birdcage, plus `stack.sh`'s first canary (harness scaffolding, idle; named
  `e2e-canary`), plus the canary under test from `smb-lure-stack.sh`
  (`e2e-lure-canary`: holder, mockingbird, OpenCanary, smb-lure, default
  enrolment, default pacing). Everything below is about the second one.
- Responder (the fixture) was started before the canary under test.
- Health was sampled through the API every 5 s from before the first
  self-test to the end (62 samples). Clocks: attacker, watcher and birdcage
  share the host clock.
- "Seconds to alert" is from the attacker's first byte to the watcher first
  seeing the alert in `GET /api/alerts?service=..&instance=..` (polled every
  0.25 s, so about 0.3 s of the figures is polling and `docker exec`). "To
  birdcage receipt" is the alert's `received_at` minus the same start.

## What looked wrong

Each is for the orchestrator to file; none was fixed here. Evidence is in the
run's raw output (`alerts-all.json`, `health-samples.jsonl`, `agent.log`).

1. **The agent's own SSH probe shows as a flagged visitor.** Every 60 s a
   non-synthetic `ssh` alert, logtype 4000, source `127.0.0.1`
   (ids 3, 55, 74, 103, 110, 115; `SESSION` 0, 2, 5, 6, 7, 8) arrives on a
   canary nobody has touched. The dashboard headlines it: "One address is
   walking the cage. 127.0.0.1 has reached all two canaries in five minutes -
   ssh, ssh", 1 FLAGGED, a SWEEP event, "never seen before tonight". The real
   attacker is a row below. (`enrol-and-hit.sh` already mentions this "SSH
   pre-login artifact"; it is not filtered from the visitor story.)
2. **Self-test SSH events are only partly marked synthetic.** From the canary's
   own address: id 27 (4000) and 36 (4001) `synthetic:false`, id 37 (4002)
   `synthetic:true`; every other self-test alert is `true`. The canary page's
   history then reads "looked at from inside - <canary> tried ssh on ssh" at
   the self-test time.
3. **A poisoner answer raises a false port-scan alert.** The answerer's UDP
   replies to the canary were reported as `portscan` from the answerer: id 100,
   `PROTO UDP`, `PORTS 53890,137,33074,56604,40513`, `synthetic:false`; agent
   log "port scan from <answerer> (UDP, 5 ports)".
4. **An SMB visit counts as one of the five scan ports.** After waiting out the
   quiet minute, one SMB open/close plus only four closed ports (20010-20013)
   raised a portscan alert with `PORTS 445,20010,20011,20012,20013`. Port 445
   is open (the lure); the detector treats it as closed.
5. **Poisoner `dest_port` is the canary's ephemeral UDP port.** Ids 57, 88,
   91, 95, 102: 48539, 53890, 33074, 56604, 40513 (137 for NBT-NS), with
   `src_port` 5355. Nothing useful appears in the port column.
6. **SMB and SNMP are shipped lures that the page does not show and the
   self-test does not test.** The canary's `ports` line and the page's
   "listening" list stop at redis 6379; the self-test row has 12 targets and
   neither is one. A dead smb-lure or snmp listener would not change health.
7. **Every enrolment records a 59-second "OpenCanary not answering" incident**
   in STATE HISTORY and 12 samples of `opencanary_down`, though nothing broke
   (agent first, OpenCanary second).
8. **The dashboard is hard to read at 1280 x 900.** Canary page: the "THIS
   AGENT" panel is cut off at the right edge and the `portscan` self-test card
   overlaps it (address, listening, bait names are clipped). Cage page: a block
   of unreadable overlapping text at the left of the trace, and the STATE
   HISTORY heading overlaps the canary cards. One viewport, one browser; wider
   screens untested.
9. **One event row describes 14 services as one visit.** "<attacker> browsed
   e2e-lure-canary :21 and tried /index.html admin / not-a-password. Said it was
   curl/8.14.1" (21 events): the port is ftp's, the path is http's.
10. **The poisoner fixture's entrypoint fails on an `--internal` network.** With
    no default route it falls back to `ip -o link`'s `eth0@if1477`, and
    Responder exits: `[!] Error: eth0@if1477: Interface not found`. The script
    starts the same Responder command on `eth0` instead. CI's network has a
    route, so CI never sees it.
11. **birdcage tries to reach github.com at start.** `WARN auth blocklist:
    common-password list refresh failed ... lookup github.com on 127.0.0.11:53:
    server misbehaving`. Harmless here (no route), but it is a default-on
    outbound fetch.
12. **`/birdcage --help` (or any unknown argument) starts a second server**
    instead of printing usage: it logs the full start-up and then
    `listen tcp :8080: bind: address already in use`. Seen once while exploring
    (a `docker exec` into the running container), not part of the scripted run.

## Limits

- The trips are hand-built protocol packets (standard-library Python), not the
  real tools: mysql, mssql, rdp, sip, tftp, snmp, redis and smb are minimal
  but valid requests. The `ssh` and `curl` trips are the real clients. A real
  `smbclient`, `snmpget`, `mysql`, `sqlcmd` or `xfreerdp` may differ.
- One attacker container on the canary's own bridge stands in for "another
  machine on the segment"; source is correct but the canary sees it as "from
  inside".
- The tested images lack batch-a's last two changes (see above).
- Disabled-by-default lures (git, https, httpproxy, llmnr service, ntp, vnc,
  tcpbanner) were not enabled or tried.
- `stack.sh`, `smb-lure-stack.sh` and `first-admin.sh` gained opt-in switches
  (`E2E_NET_INTERNAL`, `E2E_HELPER_IMAGE_SOURCE`, `E2E_SMB_CLIENT_IMAGE`,
  `E2E_KEEP_LOGIN`); unset, they behave as before.
- The per-lure journey scripts were not run: they need images built with a
  package manager.
